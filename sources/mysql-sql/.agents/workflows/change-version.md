# Cambiar una versión SQL

1. **Paso 0: versión real, después preflight.** Resuelve solo una conexión declarada en `conexiones` de `.agents/stack.yaml` por el MCP `mcp.base_de_datos`. Con una usa esa; con dos o más pregunta al usuario cuál; con ninguna no llames al MCP y conserva «no se pudo comprobar la versión real». Nunca uses otra conexión expuesta. La única sentencia de esta comprobación es `SELECT VERSION()`, en solo lectura. Si una conexión declarada falla o la herramienta esperada no existe, informa «no se pudo comprobar la versión real» y continúa sin --dato: este workflow no necesita la base; no inventes una versión. Extrae la primera coincidencia `\d+\.\d+\.\d+` de la respuesta (sin pasar ni guardar el texto crudo). Si no contiene una versión normalizable, avisa y omite el dato.
   - Con dato normalizado ejecuta `bash .agents/scripts/preflight.sh --workflow change-version --fase entrada --dato version_real=<V>` sustituyendo `<V>` por la versión normalizada. Sin dato ejecuta `bash .agents/scripts/preflight.sh --workflow change-version --fase entrada`. Exit 1 detiene; exit 2 corrige uso; exit 0 permite diseñar sin dar por pasados los omitidos. PREPARACION exige proponer el remedio y repetir con permiso, nunca saltarlo.
   - Conserva la salida y los pendientes con sus remedios de `.agents/config/codigos.yaml`. Crea RUN_DIR fuera de `.agents/` y su manifest de fases, solicitudes, salidas y revisiones.
2. **Destino y alcance propio.** Ejecuta `python3 -B -E .agents/scripts/inventario-versiones.py`. Compara `base_de_datos.version` con la versión real comprobada y la imagen esperada `mysql:<base_de_datos.version>`; presenta tabla antes/después, override y disponibilidad local. Si difieren, propone por sí solo alinear hacia stack.yaml. Si ya coinciden y el usuario pide otro destino, enumera la clave que el usuario debe editar; el usuario la edita (no hace falta regenerar: esa clave no cambia las instrucciones generadas); espera. El agente nunca edita stack.yaml ni actualiza el servidor real. Este workflow solo prepara documentación, sandbox local y objetos afectados por la versión; otros avisos son pendientes, sin incorporar sus reparaciones.
3. **Documentación y evidencia antes de escribir SQL.** Reutiliza `.agents/workflows/preparar-documentacion.md`: catálogo primero y notebook de versión exacta, usando la excepción de change-version solo para `preparar` y `cargar`, nunca para `asociar` anticipadamente. Las notas MySQL las aporta el usuario por URL: prepara el notebook, revisa sin subir con `documentacion.py cargar NOTEBOOK URL --usuario-url --tipo notas`, presenta `propuesta.aprobacion_sha256` y repite los flags aprobados con `--sha256-aprobado SHA256 --confirmar` tras su aprobación. Correspondencia y procedencia requieren sus confirmaciones cuando proceda; no inventes URL ni patrones de notas. Usa `python3 -I -B` para documentacion.py. Consulta capacidades con `preguntar mysql "PREGUNTA_GENERICA" --version V` antes de asociar; envía preguntas genéricas, nunca SQL, nombres, datos o decisiones del proyecto. Solo datos_verificados y citas verificadas entran al plan. Sin evidencia detén el cambio de objeto correspondiente y pregunta.
4. **Diseño y aprobación.** La fase `db-architect` revisa objetos del índice seguro: `python3 -B -E .agents/scripts/db-index.py --sin-datos-prueba`. Excluye siempre antes de abrir el notebook datos_prueba y sus alias; tampoco lo copies. Revisa el contenido permitido contra cambios documentados, no por antigüedad. Produce tabla objeto/ruta/celda/construcción afectada/cambio mínimo/cita, fuentes, vínculos del servicio raíz `.`, notebooks archivables, pruebas y archivos del registro. Antes de aprobar sigue `.agents/workflows/references/decisiones-stack.md`. Para VERSION_REAL ofrece sí / no / para revisión: sí incluye este trabajo local/documental; no y revisión guardan el par real/stack y alcance `["*"]`. Pide aprobación del plan completo; URL nueva requiere enmienda aprobada. Si falta edición del stack por el usuario, espera.
5. **Aplicación del plan aprobado.** Orquesta `sql-writer` para persistir solo los objetos aprobados mediante nb-edit.py, `sql-object-analyzer` para su documentación y `sql-code-reviewer` para revisar diff y citas. Usa `.agents/workflows/references/ejecutar-fase.md` para fases y manifest. No invoques la ruta de ejecución de DDL en base viva ni sql-developer contra la conexión real. Cualquier cambio adicional vuelve al plan y a aprobación; no extiendas el alcance por avisos ajenos.
6. **Sandbox y pruebas propias.** La imagen sale del stack: no hay archivo de versión independiente. Si `SQL_SANDBOX_IMAGE` fuerza otra, pide al usuario retirarlo o alinearlo; no edites configuraciones de herramientas. Si no está local, informa CONTENEDORES y su remedio al usuario; nunca hagas docker pull ni descargas. Con permiso explícito, imagen local y sandbox aislado, `sql-test-engineer` verifica solo objetos/pruebas aprobados mediante canario y pruebas compatibles. Usa lint y sandbox como en los demás workflows: los scripts gestionan sus notebooks. El agente no lee, copia ni muestra el contenido de datos_prueba; la exclusión antes de abrir sigue siendo obligatoria en detectores y en el índice de revisión de objetos. Conserva comandos, exit y salidas; fallos vuelven a implementación y revisión como cambio aprobado, sin ocultarlos.
7. **Asociación y archivo.** Ejecuta las asociaciones aprobadas de MySQL/versión/servicio `.` con documentacion.py; archiva notebooks anteriores solo sin usuarios y con confirmación. Al volver atrás reactiva el existente. Solo el script escribe documentacion.json/md. Escribe decisiones del registro únicamente dentro del plan aprobado; aplicado acredita documentación/sandbox/revisión verificados, nunca una actualización del servidor. Una fila aplicado de VERSION_REAL cubre ese par real/stack y calla la comparación; cambiar cualquiera de ambos vuelve a comprobar. No acredita una actualización del servidor.
8. **Verificación y cierre.** Repite inventario, lint pertinente y cotejo documental estricto con `python3 -I -B .agents/scripts/comprobar-documentacion.py`; para éxito cuentan tecnología/versión cambiadas, resto a pendientes. Presenta versiones finales, revisión, pruebas y controles omitidos con remedio. No ejecutes preflight al cierre ni hagas commit automático. Indica al usuario: «Haz commit de los cambios y ejecuta `bash .agents/scripts/preflight.sh`». Nunca muestres credenciales.
