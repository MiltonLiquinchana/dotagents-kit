# Preparar documentación

Ejecución manual al preparar el proyecto o cambiar una versión. Open Notebook es obligatorio. Para reparar documentación faltante entra con el validador del stack, conexión GET y diagnóstico local: no ejecutes el preflight normal hasta completar la preparación. El preflight normal siempre exige cobertura documental y nunca carga fuentes. Ejecuta las órdenes con `--confirmar` de una en una, nunca en paralelo; el script las serializa, pero cada una debe revisarse antes de la siguiente. Si `documentacion.py` responde `REGISTRO_SOLO_LECTURA` (es suyo, no del preflight ni de `config/codigos.yaml`), detente y pide al usuario que dé a la herramienta permiso de escritura sobre `.agents`; no repitas el comando hasta que lo confirme ni edites el registro a mano.

1. Valida el stack con su lector y ejecuta `python3 -I -B .agents/scripts/documentacion.py comprobar-conexion` y `python3 -I -B .agents/scripts/comprobar-documentacion.py --diagnostico`. El usuario configura Open Notebook, sus modelos y su contraseña. Si la API no pide contraseña, presenta el aviso; no cambies su protección ni los modelos.
2. Ejecuta `node .agents/scripts/inventario-versiones.mjs` y usa las versiones de cada servicio, no una versión supuesta para todo el repositorio. Excepción: si este workflow se invoca desde `change-version.md` con las versiones de destino de la tabla aprobada, usa esas versiones literales de destino solo para `preparar` y `cargar` (nunca para `asociar`). En el front el lock da las dependencias directas instaladas; en la base solo se lee la versión declarada, sin consultar el servidor. Las versiones no resolubles necesitan decisión antes de asociar documentación.
   Para toda tecnología gestionada sin versión literal cuyo detector declare `bom_propiedad`, resuelve la versión de módulo publicada: Lombok (`lombok`, BOM de Spring Boot) y, con gateway, Spring Cloud Gateway (`spring-cloud-gateway`, BOM de Spring Cloud).
<!-- si devops.infraestructura=jenkins-kubernetes -->
   Incluye Spring Cloud Kubernetes (`spring-cloud-kubernetes`, BOM de Spring Cloud) cuando se use.
<!-- fin -->
   Ejecuta `python3 -I -B .agents/scripts/documentacion.py resolver-bom --servicio NOMBRE --tecnologia TECNOLOGIA`: NOMBRE es el nombre exacto del servicio del inventario (`.` identifica el servicio raíz si aplica). Necesita red a repo1.maven.org para leer el POM público; si falta red y no hay resolución vigente devuelve BOM_RED. Presenta el diff y, con aprobación literal, repite `python3 -I -B .agents/scripts/documentacion.py resolver-bom --servicio NOMBRE --tecnologia TECNOLOGIA --confirmar`. Resuelve antes de preparar el notebook. El detector declara `bom` y `bom_propiedad`; esta última obtiene la versión literal de la propiedad publicada del POM, sin fijarla en el build. Prevalece la versión literal de la dependencia. Para Boot, después se usa la BOM explícita, el plugin del servicio y por último el stack como respaldo; una BOM y plugin locales discrepantes o expresiones no resolubles bloquean. Si Boot difiere del stack, se usa el servicio con aviso BOM_STACK; comprobar-versiones y el preflight conservan la última palabra sobre la alineación. Para Cloud se exige una versión literal única de su BOM en el servicio, sin respaldo del stack. El cotejo documental es local, sin red; cambiar la versión de Boot o el tren de Cloud deja la resolución anterior no vigente y obliga a repetir `resolver-bom`. Agrupa por tecnología y versión; los notebooks se comparten entre servicios.
3. Resuelve cada patrón del catálogo `.agents/assets/documentacion/catalogo.json` con esas versiones. Propón URL completas, tecnología, versión exacta del notebook, tipo de fuente y temas limitados. Los valores de `{ruta}` y `{tema}` se eligen de un listado real de la carpeta en el tag de la versión (`curl -s "https://api.github.com/repos/<propietario>/<repo>/contents/<carpeta>?ref=<tag>"`, solo los nombres), nunca se deducen; `{ruta}` puede incluir subcarpetas (bajar por el listado) y, si el patrón ya añade la extensión (`.adoc`, `.mdx`, `.html`), el valor va sin ella; si el listado falla (p. ej., límite de la API), pide el valor al usuario. Este listado no es la comprobación de la URL, que sigue haciendo `cargar`. Todas las candidatas empiezan «por verificar». La comprobación de marcadores (también codificados repetidamente) y redirecciones la hace el script `cargar`; no hagas un HEAD manual. Ante URL_MARCADOR completa los valores y presenta la URL corregida para aprobación. Ante URL_REDIRECCION propón la URL definitiva y pide aprobación antes de repetir la carga; no la adoptes automáticamente. Prefiere archivos del repositorio oficial en el tag de la versión, después páginas oficiales versionadas; nunca la URL actual sin versión. La referencia admite la misma serie major.minor (JDK: mayor); las notas y los requisitos exigen la versión exacta. Consulta primero el catálogo base y el del proyecto; si falta o falla una fuente, ofrece añadir un patrón o aportar una URL concreta o un archivo público externo con la sección «Fuentes aportadas por el usuario»; esa vía necesita primero el notebook de la tecnología y versión creado o reutilizado en el paso 4 (`preparar`). No descargues manuales completos ni sigas enlaces automáticamente. Pide aprobación de cada lista antes de cargarla.
4. Por tecnología ejecuta `python3 -I -B .agents/scripts/documentacion.py preparar --tecnologia TECNOLOGIA --version VERSION`. Crea o reutiliza un notebook de versión exacta y la transformación «Capacidades de la versión», no automática. Si el nombre ya pertenece a algo incompatible, detente; no lo sobrescribas.
5. Solo para cada URL aprobada ejecuta `python3 -I -B .agents/scripts/documentacion.py cargar NOTEBOOK URL --entrada ID_CATALOGO --confirmar`. Open Notebook descarga el texto público. Ante «fuente existente sin registro validado», si es una URL del catálogo, propón `python3 -I -B .agents/scripts/documentacion.py cargar NOTEBOOK URL --entrada ID_CATALOGO --revalidar --confirmar` y ejecútalo con aprobación del usuario. Cada `cargar` puede tardar aproximadamente 16 minutos; lánzala con un límite de tiempo de herramienta de al menos 20 minutos o en segundo plano y, si se corta, usa `--revalidar` para fuentes del catálogo. Después de cargar, comprueba embedded y embedded_chunks en la salida: el script espera la indexación hasta 600 segundos; no ejecutes otra sonda. Si sigue pendiente, conserva la fuente y comunica el aviso. La carga activa embeddings solo si una búsqueda vectorial limitada a ese notebook funciona; si no, avisa y sigue por chat. El script espera el procesamiento, aplica la transformación a esa fuente y comprueba la sección Versión. Informa de fuentes aceptadas, descartadas y pendientes; otra serie o unas notas de otro parche nunca se usan al preguntar. Después de cada carga el script escribe `.agents/documentacion.json` y regenera `.agents/documentacion.md`; no los edites a mano. Para cada vínculo aprobado ejecuta primero `python3 -I -B .agents/scripts/documentacion.py asociar --servicio NOMBRE --tecnologia TECNOLOGIA --version VERSION` sin `--confirmar` y muestra la vista previa al usuario; con su aprobación, repite con `--confirmar` (servicio raíz: `.`). Una tecnología fuera del catálogo se avisa; si la tarea la usa, añádela al catálogo con la sección "Ampliar el catálogo del proyecto" de .agents/workflows/preparar-documentacion.md, sin suponer capacidades de su versión. Una tecnología catalogada no admite omitir documentación: asocia fuentes válidas. Un vínculo histórico sin_documentacion se conserva y debe corregirse mediante asociación aprobada.
6. Si hace falta comprobar una capacidad, usa `python3 -I -B .agents/scripts/documentacion.py preguntar TECNOLOGIA "PREGUNTA_GENERICA" --servicio NOMBRE`. Envía solo la pregunta genérica sobre la librería, sin código, tablas, datos, rutas, credenciales ni decisiones del proyecto. Las notas verificadas no consumen modelo. Con fuentes válidas sin cambios e indexadas, se usa Ask nativo de Open Notebook; solo los datos_verificados pueden entrar en un plan, y los datos_sin_verificar se muestran aparte. Sin citas verificadas se pasa a resúmenes y, si hace falta, texto completo. Las fuentes pendientes siguen disponibles en esas dos rutas. Una cita que no coincide con el texto de una fuente admitida tras normalizar enlaces y formato no entra en ningún plan; en la cita no se eliminan atributos ni etiquetas y cualquier llave o ángulo residual impide verificarla; se conserva su texto original. Sin evidencia, pregunta al usuario. La versión y el notebook los determina la asociación del servicio; no se consulta una tecnología que no usa.
7. Si cambió la versión, presenta los notebooks anteriores administrados que se archivarán y pide confirmación. Ejecuta primero `python3 -I -B .agents/scripts/documentacion.py archivar NOTEBOOK` sin `--confirmar` y muestra la vista previa al usuario; con su aprobación, repite con `--confirmar` solo para los confirmados. No borres versiones antiguas ni leas o modifiques notebooks ajenos. Antes verifica que ningún servicio siga asociado. Para volver atrás, propone `python3 -I -B .agents/scripts/documentacion.py preparar --tecnologia TECNOLOGIA --version VERSION --reactivar --confirmar`; conserva el mismo notebook. Las retiradas de vínculos necesitan `python3 -I -B .agents/scripts/documentacion.py asociar --servicio NOMBRE --tecnologia TECNOLOGIA --quitar` sin `--confirmar` y, con aprobación, repetir con `--confirmar`, con servicio y tecnología explícitos.
8. Entrega una tabla con tecnología, versión, notebook, URL, estado y motivo de exclusión, más los avisos y lo que falta. No declares lista una tecnología sin fuentes válidas. Las decisiones del proyecto siguen en `knowledge-base/` con tgrep. No guardes la contraseña: solo se admite el nombre de su variable de entorno en stack.yaml. Incluye la tabla generada de servicio, versión del proyecto, versión documental y estado; el preflight no la actualiza: coteja el registro y comprueba conexión e IDs remotos por GET. Antes del preflight de cierre, el **usuario** hace commit de `.agents/documentacion.json`, `.agents/documentacion.md` y, si cambió, `.agents/catalogo-proyecto.json`, y luego se ejecuta el preflight. Cuando este workflow lo invoca `change-version`, que no tiene ese cierre, no aplica. Tras completar la preparación ejecuta el cotejo estricto y `bash .agents/scripts/preflight.sh --workflow preparar-documentacion --fase cierre` sin omisiones; no declares lista la entrega si quedan bloqueos. El diagnóstico no sustituye esta validación final.

## Ampliar el catálogo del proyecto

Si una tecnología que usa la tarea no está en el catálogo, amplía `.agents/catalogo-proyecto.json`. El archivo lo escribe solo el script (`ampliar-catalogo`), nunca el usuario ni el agente a mano; si el archivo no existe, equivale a catálogo vacío.

1. Propón la entrada con identificador, nombre legible, detector y fuentes oficiales por versión:
   - Detectores de Gradle: tipo `dependencia` con `identificador` (`grupo:nombre` exacto) o `prefijo`, tipo `plugin` con `identificador` del plugin, tipo `bom` con coordenada de la BOM, o tipo `bom_gestionado` con `identificador` de la dependencia y `bom` con la coordenada de la BOM que fija su versión (p. ej. `org.springframework.cloud:spring-cloud-dependencies` o `org.springframework.boot:spring-boot-dependencies`).
   - Para dependencias gestionadas por una BOM: si una BOM admitida (Spring Boot o Spring Cloud) publica una propiedad con la versión del módulo y las fuentes oficiales se versionan por módulo, usa un detector de tipo `dependencia` con `identificador` exacto, `bom` y `bom_propiedad`; resuelve esa propiedad con `resolver-bom` antes de preparar el notebook. En otro caso usa `bom_gestionado`: la versión asignada a esa tecnología es la versión de la BOM (p. ej. OpenFeign gestionado por `spring-cloud-dependencies 2025.1.1` queda en `2025.1.1`, no en la versión interna de OpenFeign); el notebook se nombra con esa versión de la BOM y las fuentes deben ir versionadas por esa BOM. El diagnóstico muestra de qué BOM proviene (`origen_bom`). OpenFeign conserva la versión del tren; Lombok y Spring Cloud Gateway usan la propiedad publicada de su BOM admitida para obtener la versión del módulo.
<!-- si devops.infraestructura=jenkins-kubernetes -->
     Spring Cloud Kubernetes también usa la propiedad publicada de la BOM de Spring Cloud para obtener la versión del módulo.
<!-- fin -->
   - Fuentes oficiales por versión: identificador único P1, P2… (nunca B, F o S), tipo (`referencia`, `notas`, `migracion`, `requisitos`), URL pública (sin credenciales) con marcadores `{version}` o `{serie}`, y estado inicial `por verificar`.
   - Un detector que reconozca una coordenada ya cubierta por el catálogo base o por `cubiertas_por_boot` bloquea, igual que redefinir una tecnología o fuente existente.
2. Muestra primero la propuesta y su diff sin escribir:
   `python3 -I -B .agents/scripts/documentacion.py ampliar-catalogo --tecnologia ID --nombre "NOMBRE" --detector 'JSON' --fuente 'JSON'`
3. Con la aprobación literal del usuario, repite la orden añadiendo `--confirmar` para persistir la entrada en `.agents/catalogo-proyecto.json`.
4. Vuelve a ejecutar el diagnóstico: `python3 -I -B .agents/scripts/comprobar-documentacion.py --diagnostico`. La tecnología pasará a requerir documentación en los servicios que la detecten; procede entonces con los pasos normales de preparación, carga y asociación.

Para añadir fuentes con patrón a una tecnología ya existente (del base o del proyecto), usa `python3 -I -B .agents/scripts/documentacion.py ampliar-catalogo --tecnologia ID --fuente 'JSON'`, sin `--nombre` ni `--detector`. Solo añade fuentes; cualquier redefinición de la tecnología o colisión de IDs sigue bloqueando. Presenta el diff sin escribir y repite con `--confirmar` tras aprobación literal. Todas las fuentes del proyecto tienen id P1, P2… y patrones HTTPS con `{version}` o `{serie}`; nunca se usa una URL concreta sin versión como patrón.


`--fuente 'JSON'` se repite una vez por cada fuente en la misma orden completa de ampliación. La oficialidad la decide el script con `dominios_oficiales` del catálogo, comparando host y ruta (incluido el propietario en hosts compartidos). Al definir una tecnología NUEVA del proyecto se pueden proponer esas reglas mediante `--dominios-oficiales '[{"host":"docs.example.invalid","ruta":"/herramienta/"}]'`; son parte del diff y solo se guardan tras aprobación con `--confirmar`. No se pueden añadir ni redefinir dominios oficiales de una tecnología base; añadir fuentes a ella no permite hacerlo.

## Fuentes aportadas por el usuario

Primero ofrece las fuentes del catálogo. Para esta vía ejecuta primero el paso 4: `python3 -I -B .agents/scripts/documentacion.py preparar --tecnologia TECNOLOGIA --version VERSION`, y usa el notebook devuelto para esa tecnología y versión. Si las fuentes no sirven o faltan, el usuario puede aportar una URL pública HTTPS de cualquier sitio o un archivo público externo al repositorio; no debe contener credenciales ni datos del proyecto. Informa tecnología, versión, tipo, procedencia oficial o no, tamaño y hash antes de pedir aprobación. Una fuente no oficial se registra `oficial: false`: no acredita origen del fabricante/proyecto y requiere aviso y aprobación expresa, pero no se rechaza solo por ello.

Para revisar sin subir: `python3 -I -B .agents/scripts/documentacion.py cargar NOTEBOOK URL --usuario-url --tipo TIPO`, o `python3 -I -B .agents/scripts/documentacion.py cargar NOTEBOOK --archivo RUTA --tipo TIPO --documentacion-publica`. Elige `--tipo TIPO` (referencia, migracion, notas o requisitos). La segunda opción exige declaración expresa de documentación pública; están bloqueados los archivos dentro del repositorio (también por enlaces simbólicos), rutas protegidas y posible contenido protegido sin excepción. No abras secretos, .env*, account/ ni kubeconfig para escanearlos. El límite es 10 MiB; se admiten PDF textual, HTML, Markdown, texto y AsciiDoc. Un PDF necesita extracción local con pdftotext; si no puede inspeccionarse, aporta texto y no instales herramientas automáticamente.

El script comprueba marcadores y redirecciones también para usuario-url; solo omite la regex de catálogo y la versión en la ruta. Descarga únicamente la fuente indicada para inspección local, sin ejecutar HTML ni seguir enlaces. Evalúa en el contenido la tecnología y versión con la misma validación de correspondencia que se aplica después de la carga. Si falta o es ambigua, avisa y solicita confirmación separada; repite la revisión con `--confirmar-correspondencia` solo después de recibirla. Una versión o tecnología explícitamente incompatible bloquea. La revisión usa la tecnología y versión del notebook indicado. La confirmación de correspondencia no convierte texto inventado en cita; el hash aprobado se coteja con los bytes de la fuente, sin una vinculación persistida de esa aprobación al notebook.

Revisa con el usuario `propuesta.aprobacion_sha256`: es el hash de los bytes descargados o del archivo, distinto del sha256 del texto extraído que protege las citas. Con aprobación de esa fuente y procedencia, repite la orden con `--sha256-aprobado SHA256 --confirmar` (y los flags ya aprobados). Si cambian los bytes, se requiere otra revisión. Para acreditar la procedencia oficial de un archivo se puede indicar `--procedencia-url URL_PUBLICA`: el script comprueba esa URL y decide `oficial` con las reglas `dominios_oficiales` del catálogo (host y ruta); un nombre de archivo no acredita oficialidad. Sin procedencia acreditada, el archivo es no oficial.

Los archivos se suben por multipart a Open Notebook, nunca por su ruta local. Se registra origen catalogo/usuario-url/usuario-archivo, oficialidad y sha256 del texto extraído; para archivos, nombre base y archivo_sha256 de los bytes, nunca ruta absoluta. Tras la ingestión se valida el contenido con validate_insight y se comprueba la URL final. Para archivos se conservan los bytes aprobados sin exigir igualdad entre extracciones. En usuario-url, una diferencia de texto produce AVISO FUENTE_TEXTO y continúa la validación; una URL final distinta o contenido incompatible deja la fuente excluida, sin borrarla ni recargarla automáticamente. El registro antiguo formato 1 sigue leyéndose sin modificarlo; la escritura aprobada usa formato 2. Solo el script escribe documentacion.json, documentacion.md y catalogo-proyecto.json.

## Migración

Retira la antigua clave del MCP de documentación del stack del proyecto y añade las claves `documentacion.*` desde la plantilla; el generador no sobrescribe tu stack. Configura sus valores y regenera. No hace falta configurar un MCP para esta integración REST.

Antes de aprobar cualquier plan, sigue `.agents/workflows/references/decisiones-stack.md`; consulta clases, remedios y códigos que resuelve este workflow en `.agents/config/codigos.yaml`.
